# Audit, 2026-08-16 — findings and where to go next

A read-only audit of all three repos, across seven dimensions: dead logging,
optimization, unused features, oversights, robustness, the F1 overlay, and
direction. Every finding was put to an **independent verifier** before anything
was implemented; **39 survived, 15 were refuted.** That ratio is the most useful
number in this document — better than one finding in four, from agents reading
carefully, was wrong. Several of the refutations are recorded below because the
mistake is the reusable part.

**Status vocabulary, as always here:** *verified* = read in the code and cited.
*Landed* = written and invariant-checked. *CI-green* = the Windows build passed.
*Tested in game* = the owner ran it. **Nothing in this document is tested in
game.**

---

## 1. What the verifiers caught, and why that is the finding

Four proposals would have made things worse and were stopped before implementation.
They are listed first because the pattern repeats and is worth recognising.

| Proposal | Why it was wrong |
| :-- | :-- |
| Delete `drawmeta` as dead code | It has no producer, but it is not dead — on 2026-08-14 it **replaced** the exhausted `D3DMATERIAL9` side-channel band. Deleting it would have re-imposed a constraint the project had just removed |
| `warn_once(0xA100 \| (width << 16) \| height, …)` | `0xA100` occupies bits 8–15, which `height` also occupies. The tag aliases into the height and the two call sites stop being distinct — a silent key collision in a deduplicating log |
| Guard a redundant matrix upload on `(g_skin.palette, j)` | `g_skin.palette` is a **pointer**. Pointer identity does not capture content, so the guard would suppress uploads that were needed |
| Settle `texrep`'s `awaitingReplacement` on a frame timeout | Reintroduces the documented "preserve-path latch" regression: a room stays low-res for its whole life and sharpens only after a reload |

And one where the reviewer was wrong and the implementer said so: a claimed
off-by-one in the sky-stats fallback was **itself** off by one — the counter is
pre-incremented, so `> kMaxFramesInFlight` is N frames, not N+1. The number was
left alone and the comment reworded to the mechanism.

**The reusable lesson:** three of the four bad proposals were arithmetic or type
errors inside a change that was conceptually correct. Reviewing the *idea* would
have passed all of them.

## 2. Kakariko — do not shelve it. It is now one warp and one log

The owner was close to abandoning this, reasonably, after a day of elimination
that produced nothing. The situation has changed, and all three preconditions
for a decisive attempt are now in place:

- **Backtraces symbolize.** `CMakeLists.txt` defines `DUSK_CRASH_DBGHELP=1` for
  every Windows build, not just Debug (`fd10d57a`), and `crash_handler.cpp` walks
  `*ep->ContextRecord`, i.e. the *faulting* thread — which matters because all
  four frames are on a Remix worker. The fork's `release` flavour emits and ships
  PDBs. **This has never been exercised.**
- **A real suspect landed.** `SceneManager::prepareSceneData` recreates the
  opacity micromap manager on a camera cut, and the recreate path called
  `removeEventHandler` and nothing else — while the disable branch eight lines
  below calls `invalidateOpacityMicromapBindings()` and `notifySceneChanged()`
  first, for the same destruction. `mergeInstancesIntoBlas` then runs seventeen
  lines later **in the same frame**, free to restore cached buckets whose BLASes
  reference the destroyed manager. A warp is a camera cut. **This is consistency,
  not evidence** — no fault has been traced to it, and the fix's own comment says
  so in those words.
- **Two bounded diagnostics** now print at the cut (`ommSeed`) and sixty frames
  later (`postCut`). `postCut` sits deliberately **outside** the OMM block, so it
  survives the `rtx.opacityMicromap.enable = False` comparison — a diagnostic
  that vanishes under the test it exists to be compared against answers nothing.

**The ask is one session, two warps:** Hyrule Field → Kakariko as normal, then
again with `rtx.opacityMicromap.enable = False`. Send the crash report and the
Remix log. That yields the symbolized frame *and* the OMM answer together.

Do **not** ask the owner to describe anything, and do not ask them to symbolize
by hand — that request was made once in this project and was correctly refused.

**One cheap change worth landing before that run:** the crash report names the
game build (`DUSK_WC_DESCRIBE`) but not the Remix build, and correlating the two
by hand has already wasted rounds. The fork's `getRtxOptionValue` export already
returns a string buffer, so the Remix build string can be read into the crash
report header. One crash file would then name both binaries.

## 3. The highest-leverage item in the project is a broken test script

> **RESOLVED 2026-08-17.** The finding below is kept as written, because it is
> the audit record. What changed: the missing `JPADynamicsBlock.h` stub and the
> other stub gaps were added, all **45 checks pass** under ASan and UBSan with no
> check weakened, and `.github/workflows/invariants.yml` now runs the harness on
> every push and pull request. Two of the six gaps this audit listed turned out
> to be already stubbed, and one named the wrong `getPrmClr` overload — the
> corrected list is in `docs/effect-lights.md`. The follow-on suggestion below
> (water and emissive classifiers as the next suites) is **not** done.

`tests/effect_lights/run.sh` is the **only** behavioural test suite in any of the
three repos — 45 checks, under ASan and UBSan. It is the only mechanism that can
verify behaviour without spending one of the owner's scarce in-game test windows.

It has not compiled since **2026-08-09** (`effect_lights.cpp` gained a
`JPADynamicsBlock.h` include that the stub headers never got), it is in **no CI
workflow**, and `docs/remix-open-issues.md` asserted it as live verification with
no caveat. So the project believed it had a safety net it did not have.

Repairing it and putting it in `invariants.yml` — which is already ubuntu-24.04,
already unfiltered by path, already runs in seconds — is worth more than any
individual rendering fix, because it is the only thing here that converts
"someone should test this" into "CI tested it".

**If a second suite follows, the water and emissive classifiers are the obvious
candidates.** Both are pure functions over names and colours
(`water_materials.hpp`, `rtx_dusklight_emissive.h`), both are currently untested,
and both are untestable today except by looking at pixels.

## 4. Untested-but-landed work is accumulating, and it cross-contaminates

The playbook's newest section is dated **2026-08-11**. Since then these have
landed and never run:

| Feature | Recorded status |
| :-- | :-- |
| Fog rework — top-up ramp, density cap, dome-derived ambient, forward scattering | landed 2026-08-13, untested |
| Exposure-relative fog level | landed 2026-08-13, untested |
| Dusklight panel settings persisting | landed 2026-08-13, untested |
| Water on the `Power` transport | untested |
| The two-colour ramp | CI-green, untested |
| Capturable API assets | CI-green, untested |
| Room lights | built, never run |
| The ambient grade | built, never run |
| Everything in this audit | landed today, untested |

This is not merely a queue. **These items interfere with each other**: the grade
"must be tested *alone*, and ideally not until open issue 4 is fixed", and
running two light systems together "looks exactly like the new placement being
broken". A test window spent in the wrong order produces evidence that cannot be
interpreted.

**Recommendation:** rewrite the playbook as a single ordered session script, one
entry per untested item, each with (a) the one option to flip, (b) the exact log
line or tab readout that decides it, and (c) its regression signature. Order it
so mutually-contaminating items never overlap. The fog log
(`rtx_dusklight_atmosphere.cpp`) is the model — it already prints ramp, sigma,
cap reason, excess peak, ambient split, exposure correction and mode names in one
self-describing line.

**Then add one overlay button: "Log Dusklight State Report".** Two such buttons
already exist (texture categories, effect lights). Today the atmosphere, water,
emissive, texrep and material paths only report passively on *first sighting*, so
a session that walks past the interesting moment cannot ask again. One press that
dumps every subsystem's live state is the same instrumentation-before-fix move
that made effect lights answerable.

## 5. Give `drawmeta` its first producer — and make it the join nobody can do

`dusklightSetDrawMeta` is built end to end — aurora reserves `0x0058`, decodes
it, and resolves the export by `GetProcAddress`; the fork peeks it into
`LegacyMaterialData` — and **nothing in the game calls it.** So the transport
that now replaces the whole side-channel band has never been exercised.

Open issue 14 states its own conclusion: *"Nobody has resolved any hash to any
asset, and there is no instrument in either repo that can — which is the actual
finding here."* The far side of that join already exists: `matrep.rmx` prints
`tex0hash`, the hash Remix shows in its own categorization UI.

**So the first producer should close that gap.** Add a `sourceTag` field, have
the JPA draw path set it to the effect ID, and print it in `matrep.rmx` beside
`tex0hash` and in the effect-light report. That produces, in one log: symptom →
effect name → texture hash → Remix's own UI, with no owner judgement anywhere in
the chain. It also gives the transport a real exercise before something
load-bearing depends on it.

`J3DMaterial::load` is the template — it is the one place in this engine that
brackets exactly its own draws, and its comment block is the written-up solution
to the schedule-versus-issue problem the drawmeta commit named as its blocker.

**Do not take `Ambient.a` for this.**

## 6. What else to delete

`localLights` is gone (protocol 17, this session): ~350 lines game-side, seven
fork options, an overlay section, four readouts, and a panel in the game's own
ImGui that fixed-function mode never draws. The A/B it was kept for was decided
on 2026-08-07.

Remaining candidates, in order of confidence:

- **`Emissive.a`, the evidence score.** Aurora still computes and ships it;
  the documented position is that **nothing decides on it** — three revisions cut
  on it and all three missed the lava, which scores 0.00. It is still printed in
  the log, which is a defensible reason to keep it. *Not verified end-to-end in
  this audit; confirm both sides before removing.*
- **`effectLightDerivedReach`.** Retired at protocol 14, replaced by
  `effectLightReachScale`. A config setting the old name is inert **and silent**,
  which is the part worth fixing even if the name stays.
- **`rtx.dusklight.water.wavesAsBlend`.** Added and reverted to default false
  within one week. It survives in the owner's `rtx.conf` as `True`, which the
  default revert cannot reach — so it should either be removed or the stale key
  should be called out.

**And one anti-recommendation:** `roomLights` looks like a third redundant light
system and is not. It surveys the room's own authored lights — a different
registry, the only one in the game carrying a cone — and its logging runs whether
or not the option is on, so it answers questions the other two cannot.

## 7. Standing hazards this audit did not remove

- **`RtxOptions.md` is now missing 104 `rtx.dusklight.*` options and lists 8 that
  no longer exist** (up from 1, because of this session's deletions). It is
  generated by running the DLL on Windows and cannot be refreshed from a Linux
  checkout. Regenerate at the next Windows checkpoint.
- **The MinGW harness does not cover `settings.cpp` or
  `ImGuiRemixBridgeWindow.cpp`**, which is where the settings triple and the
  removed panel live — the two files most likely to break from a deletion. Worth
  adding.
- **`J3DMaterial.cpp` and `water_materials.hpp` are not in the harness either**,
  though both were changed this session.
- **Nothing can see an unmerged branch.** Protocol 17 was verified free against
  all 11 live `claude/*` branches by hand. `claude/kasumi-naming-correction-w3e204`
  still holds 12; the next branch takes **18**.
