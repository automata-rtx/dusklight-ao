# Remix integration: open issues and untested work

The volatile half of the Remix effort, and **the project's single "not verified
in game" ledger.** [`kankyo-remix.md`](kankyo-remix.md) is the stable design
reference; [`remix-test-playbook.md`](remix-test-playbook.md) is what to run
next. Four parallel verification ledgers is why three of them went stale — a
status claim belongs here and nowhere else.

**The game symbols named below are romanized Japanese** — `dKyr_drawSibuki`
draws 飛沫 *shibuki*, spray. [`japanese-naming-remix.md`](japanese-naming-remix.md)
explains why a grep for one of them can come back empty for a symbol that exists.

**Rule for this file: an entry states its evidence and its confidence.** Three
sessions have written a plausible story here as though it were a finding, and
one of those shipped a fix that did nothing. If a cause is inferred rather than
read, say so. And "correct in raw D3D9" is *evidence about where a defect
lives*, never a requirement being met — the raw image is never shown.

**Protocol is at 17.** `kRequiredProtocol` is a file-scope `constexpr` in
`dxvk-remix/src/dxvk/imgui/dxvk_imgui.cpp:2613`, read by the overlay's status
strip; bump both sides in one commit. The tab's readout and the fork's
`CLAUDE.md` are the authorities, not this line — it has been stale twice.

`emissive.brightness`, and `dxvk-remix/RtxOptions.md` still carries the old row.
That file is **generated by running the DLL on Windows**, cannot be refreshed
from a Linux checkout, and is stale in both directions; the `RTX_OPTION`
declarations in the fork's `rtx_dusklight_*.h` are the authority, and
`dxvk-remix/scripts/check_dusklight_invariants.py` prints the live drift count
on every run. **Do not restate that number from memory.**

## Live issues

Each entry: symptom, what is established, what was ruled out, next step.

**1. Crash entering some levels — downgraded 2026-07-29, do not close.**
`EXCEPTION_ACCESS_VIOLATION` reading `0x10`, inside `d3d9.dll` on a Remix worker
thread, during a cutscene transition after a camera cut. The NaN guards added to
both light paths are **plausible as the fix, not demonstrated** — one long
session with many warps produced no crash, but the original was intermittent.
Next step if it recurs: bisect with `rtx.dusklight.game.bridgeEnable = False`,
then `rtx.neuralRadianceCache.enable = False`. Probably the same fault as the
Kakariko crash below, which reproduces 100% and is the one to work.

**5. Wolf senses renders as an opaque overlay.** A heavy black surround with a
pure white centre where the see-through region should be. **Not investigated at
all.** It blocks the wolf-senses route to testing the mono overlay and composite
base weight — **not the twilight route**, which reaches the same code through
bloom tables 1/2 and is how that test should be done.

**6. World-space UI billboards appear only intermittently.** The targeting arrow
and torch fire billboards appear together, inconsistently, only while the
letterbox bars are up (necessary, not sufficient); under shadow the arrow goes
dim. Neither shows in Remix's texture categorization screen.

*Established, read in the fork:* `isRenderingUI()` (`d3d9_rtx.cpp:561`)
classifies the first orthographic, z-write-disabled draw on the primary RT as UI
and triggers RTX injection; `internalPrepareDraw` (`:575`) then early-returns for
every remaining draw in the frame. A post-injection draw never enters the
raytraced scene, so its textures are never categorised — the symptom exactly, and
**no dev-menu tagging can reach these draws**, since `rtx.uiTextures` is consulted
*inside* `isRenderingUI()`. The boundary is in the fork, so moving it is on the
table. It also settles that the targeting cursor **is not UI and never was** (a
perspective-projected J3D model, `d_attention.cpp:1619`), so "dim under shadow" is
the correct result of path-tracing it — the cursor and the flames share a position
relative to the boundary, not a code path.

*Ruled out with evidence:* 2D draw-list overflow, `GXPeekZ`, `GX_DEBUG_GROUP`.

*Open:* why the letterbox helps — `trimming()` sits *after* both draws, so
something else correlated with the bars must inject earlier. **Worth flipping
around:** for a UI arrow "correct" probably means flat and unlit, which is the
*post*-injection path.

*Next step, cheapest first:* log `m_drawCallID` when injection triggers, with and
without bars — two numbers settle it. Then
`rtx.skipDrawCallsPostRTXInjection = False`, then `rtx.drawCallRange`. The flame
half is parked and probably is not this issue.

**7. Grass patches shade wrongly under Remix.** Blades glow in the dark or come
out too dark, with a very delayed lighting response.

*Established:* `dGrass_packet_c::draw` batches every blade into four buckets and
emits them pre-transformed in one stream, so the asset hash churns every frame
and the patch carries no denoiser history. The per-blade path — display list plus
`GXLoadPosMtxImm` — already exists in the same function and gives a stable hash.
`perBladeGrass` (protocol 5) and `perBladeFlowers` (protocol 13) build it, both
off by default, **both untested.** `perBladeGrass` covers `dGrass_packet_c`
**only**; `daGrass_c` also plants 花 *hana*, flowers, through `dFlower_packet_c`,
which had the identical batch and no switch until 2026-08-11 — so a flower
showing the symptom would not have moved for it, which reads as *the diagnosis
being wrong* rather than as the coverage being partial. Regression signature: a
frame-rate drop with either on is the per-blade path costing what the batching
saved, which is why both default off; flowers vanishing or drawing untextured
means the vertex descriptor or the ambient reuse is wrong, not the idea.

*The other two symptoms are separate.* Glow in the dark — one-click test is
`rtx.enableEmissiveBlendModeTranslation = False`; if it stops, tag grass rather
than disable the feature globally. Too dark — grass is drawn with GX lighting
*on*, so its vertex colour was one input to a lighting equation and was consumed
as finished albedo; the per-draw verdict (closed issue 10) should now exempt it.
**Inference from the `GXSetChanCtrl` call, not measured** — `vtxUse=` on grass's
`matrep.sum` line is the first thing to read.

**8. Materials read greyscale — largely fixed, last revision untested.** Remix
rebuilds a material from one texture stage and an argument it cannot decode
resolves to identity, so a lost colour term *bleaches*. **The finding worth
keeping is that the material shape everyone assumed does not exist here:**
measured over 111 real materials the dominant shape is a two-colour ramp,
`lerp(colourA, colourB, texture)` — one rupee texture yields seven rupee colours
that way — and a multiply is only the special case where colourA is black. The
fork now evaluates the GX combiner from both endpoints, exact for every ramp
material. **CI-green, untested.** `ramp=` says which path applied; a material
reading flat, or with its ends inverted, means the endpoints were swapped rather
than approximated. *The framing:* "Remix cannot express X" was true of **stock**
Remix and was treated as permanent for a week.
`extern/aurora/docs/dx9/remix-material-interface.md` §10.

**9. Emissive surfaces — rev 4 tested good 2026-08-06; one thing left.** The rule,
the measurement behind it, and why three earlier revisions all missed the Goron
Mines lava are in the fork's `rtx_dusklight_emissive.h` header comment and in
`extern/aurora/docs/dx9/remix-material-interface.md` §9. In game it caught the
lava and read as properly molten.

*Left open: the grey lava geysers.* `grp=` carries the material's authored name
since 2026-08-11 but only under `DUSK_MAT_LABELS=1`
(`libs/JSystem/src/J3DGraphBase/J3DPacket.cpp:245`), and every session so far ran
without it — so which logged material is the geyser was inferred from texture
size, format and ramp endpoints rather than known. **Re-run with it on before
treating the geysers as unexplained.** Also unconfirmed: whether the per-material
derivation holds for a small pickup as well as for lava.

**11. Item drop-shadows render as a black quad.** *Rewritten 2026-08-11; the old
mechanism does not survive a read of the source.* It blamed a projected texture
transform; the shadows it names are **the class that does not use one**.
`d_drawlist.cpp:1637` sets a projected `GX_TG_MTX3x4` before the **real** loop,
`:1678` an ordinary `GX_TG_MTX2x4` before the **simple** one, and
`dDlst_shadowSimple_c::draw` never changes it.

*First check, and it costs nothing:* `rtx.dusklight.game.blobShadows` shipped
2026-08-05 and was tested good on exactly these item shadows. If the black quad
is still there at its default, this is not that class. *The instrumentation gap:*
the discriminating fact is the texgen type, and there is **no texgen type in any
`matrep.*` line** — checked against the emitter at
`extern/aurora/lib/dx9/dx9_tev.cpp:1824`; adding it to `matrep.gx` is the cheap
version. Two corrections, both verified: the log string the old entry quoted is
**not in the fork**, and **the fork now supports projected texcoords**
(`d3d9_rtx_utils.cpp:128`), so aurora's `unsupported-effects.md` R6 needs
re-checking. *One lead, NOT a diagnosis:* the simple shadow is a five-pass
shadow-volume sequence — framebuffer-alpha arithmetic, not a picture.

**14. Drool renders as a UI element while targeting; nearby particle effects
degenerate into white quads. Cause UNKNOWN.** Reported 2026-08-09 at a Deku Baba.

*A first pass blamed texture tagging and that was wrong*, kept as a caution: a
hash was found in `worldSpaceUiTextures`, a matching symptom was found, and the
two were connected with nothing joining them. The owner, who tagged the textures,
states they are unrelated. **Nobody has resolved any hash to any asset, and there
is no instrument in either repo that can — which is the actual finding.**

*Established independently:* the launch-dumped `rtx.conf` has hash
`9EE4883FDEEB8478` in **six mutually contradictory categories at once**;
`worldSpaceUiTextures` makes Remix force emission on at intensity 2.0
(`rtx_instance_manager.cpp:1107-1114`); `particleTextures` routes into billboard
creation, which aborts for the whole instance unless the index pattern is
`A,B,C,A,C,D`. The billboard warning in the log proves less than it looks — it is
wrapped in `ONCE` and fired ~7 s into a 12-minute session, so any later
occurrence was silent.

*Next step:* the effect report must carry the hash Remix will see for an effect;
until it does, diagnosing "this effect renders wrongly" is guessing. Untested
candidates: a tag on an asset shared between contexts; the game drawing the
effect in a 2D group (`dPa_group_id_change`, `d_particle.cpp:213-218`, puts
`resUserWork` bit `0x2000` into group 14 — checkable the moment `resUserWork` is
in the report); instance batching carrying one draw's category onto another.

**15. Water renders as a milky white sheet.** Four independent causes, only some
addressed — "water is broken" was treated as one defect for two sessions and it
is not. **The MAxx taxonomy, the fall-through to `OpaqueMaterialData`, the 1×1
`0x00FFFFFF` placeholder that makes it white rather than merely wrong, and why
every constant is an option are all at
`dxvk-remix/src/dxvk/rtx_render/rtx_dusklight_water.h:24-58`**; the per-layer hide
switches carry their own reasons in their option descriptions.

| # | Cause | Status |
| :-- | :-- | :-- |
| 1 | Every layer fell through to `as<OpaqueMaterialData>()` | marked draws now become translucent; **the mark is measured working** (2026-08-08, 11 materials) |
| 2 | Projective texture transforms were discarded | fixed, CI-green, untested |
| 3 | Aurora drops indirect texturing — the ripple *warp* | untouched |
| 4 | The TEV two-constants-per-stage ceiling, 48 hits in one session | untouched |

*Water is not one draw.* Four of the 11 materials arrived `texXform=3 proj=1` —
`MA02`/`MA10`, a camera-projected painted reflection over water Remix traces for
real anyway. The mark therefore carries a role (`NONE`/`SURFACE`/`PROJECTED`)
packed with the tag and the layer into `D3DMATERIAL9::Power` as
`tag * 100 + layer * 10 + role`; `PROJECTED` is hidden by default. **The transport
was rebased 2026-08-11** out of `Ambient.g`/`.b`/`.a`, which HD texture packs
already owned — merging it as written would have deleted texture packs silently.
**Untested on this transport.** The tag-based control the per-layer switches
replaced was wrong: MA06 is the waves *and* the shoreline *and* the murk.

*Two dead ends, so they are not re-derived.* Binding the draw's own colour texture
into the normal slot was **reverted 2026-08-09** — a colour texture decoded as a
tangent normal is noise, and on a lake with an authored normal map it added a
*second* one, which per an RTX Remix rendering engineer does not blend correctly.
And an additive pass does **not** mark "light over a surface" here: measured over
seven surfaces, `SRC_ALPHA,ONE` holds both a still pass and scrolling ones.

*The real cost to weigh:* per-hash replacement **is** tagging — one authored
normal map re-keyed to every water texture in the game, and water in an unvisited
area showing raw-colour noise until someone finds it. One normal map for every
water draw is the translation-shaped answer; not built.

*Regression signature, worst first:* non-water materials turning translucent (the
mark leaking — the 2026-08-08 20:35 failure); water geometry *vanishing* (the
projected mark leaking); the texture at the wrong scale or not moving; a milky
ring at the water's edge; water invisible rather than transparent
(`transmittanceMeasurementDistance`, 200 and **still an uncalibrated guess**).
Four log lines trace the mark end to end, ending at `dusklight.water tex0hash=…`
in the Remix log. **One trap when reading the image instead:** a hand-authored
replacement wins in `determineMaterialData` *before* the water check, so
translucency on some water is not evidence the mark landed —
`dusklight.water.replaced` is what says it did.

**16. Volumetric fog rework — the defaults are tested; mode 2 is not.** Landed
2026-08-13, hardened 2026-08-17/18, **tested in game 2026-08-18 and the owner
reported improvements.** That covers the shipping default path: `fogRampMode` 1,
`fogColorSpace` 1, `fogColorDirectional` false, the anchor correction and the
`rtx.fogColorScale` bypass. **`fogRampMode` 2 and `fogRampFloor` are NOT
covered** — mode 2 is not the default and nothing switched it on. Fork-only, no
protocol bump. Derivations:
`dxvk-remix/documentation/DusklightAtmosphere.md` §5.1–§5.4.

*The four causes were all read from source and are derived in the fork's own
code* (`rtx_dusklight_atmosphere.cpp:371-412` for the anchor, `:544-547` and
`:1153-1165` for the dome): the medium could not be clear where the game is
clear; the two halves of our own fog converged to different levels by 4.4× and,
undetected for four days, to different *colours*; **the fog is never lit by the
sky**, the RTXDI light list having no dome light; and
`rtx.volumetrics.anisotropy` was 0.

*The revert is not `fogRampMode = 0`.* It is `fogRampMode = 1`,
`fogColorDirectional = True`, `fogColorSpace = 0`. The `rtx.fogColorScale` bypass
and the anchor correction have **no** revert switch, both being straight
corrections — and the anchor correction makes every scripted fog bank 4.46×
denser.

*Regression signature.* Near-field haze *thicker* than before means the cap is not
binding — check "peak excess" against `clearZoneTolerance`. Shafts that vanished
mean the cap took too much density. Outdoor fog brighter than the terrain in
front of it means the dome average is too strong. **The mode 2 signature has a
qualification that would otherwise fire on a correct build** — see
[`remix-test-playbook.md`](remix-test-playbook.md) §3, which is where the mode 2
run is queued. In short: the top-up residual must be flat *within the froxel
grid's reach* and varies by construction past it — and past-the-reach is the
common case outdoors, so the unqualified version of this signature would have
fired on a correct build the first time anyone stepped outside.

## Closed

One line each; the clause after the dash is the only part still worth having.

- **0 — local point lights work** (2026-07-29) — closed **without a proven root
  cause**, so if effect lights ever lose colour or reach, re-read `pointlight[]`
  and `efplight[]` rather than assuming the old diagnosis.
- **2 — the night shadow wandering was the moon billboard** (2026-07-29,
  `hideSkyBillboards`) — **if the moon is wanted back, paint it into the
  generated dome**: visible, correctly placed, contributing light, and
  structurally incapable of casting a shadow.
- **3 — local light defaults `19` and `10`** (2026-08-06) — 19 is the derived
  reading of the game's attenuation curve rather than a taste call, the two
  interact, and both carried over to effect lights unchanged.
- **4 — the fog medium dimmed the generated sky** (2026-08-13, `skyFogMode` =
  Exempt) — the lesson outlives the fix: *a guard in one path is not a guarantee
  across the system*, the composite having reached the sky twice.
- **10 — vertex colour carries baked lighting on *some* draws** (2026-08-04 in
  code, untested) — **the signal is the pair, not the lighting bit alone**:
  `lit=0` with `matSrc=GX_SRC_VTX`, 44 of 117 measured materials. Regression: a
  surface gaining or losing brightness and saturation this round is this change.
- **12 — HUD fade-in effects drew as opaque squares** (2026-08-04, untested) —
  **the one change that touches opacity, and opacity still has to rasterize
  correctly**, so its regression is alpha-tested foliage, grates or grass going
  solid or vanishing, which outranks every other result in a session.
- **13 — dense weather particles were a draw-call problem** (rain and snow tested
  2026-08-08; Twilight fog and bog untested) — **the durable question is never
  "does this batch?" but "is there a stable identity here to destroy?"** Grass has
  one, particles do not. `dKyr_evil_draw2` is deliberately left unbatched: the
  trade on offer was the fog's material for its draw count. Still owed: one
  `kankyo.particles` line from `D_MN08` — see the ledger above.
- **17 — the F1 panel never persisted** (2026-08-13, untested) — every control
  wrote to the `Derived` layer, which is never serialised, so the value took
  effect, read back correctly, and was dropped at save time with nothing logged.
- **18 — the sand worm carried a light the original never had** (2026-08-13,
  untested) — sun-lit sand is exactly what the additive-and-glow rule cannot tell
  from a flame. **The last step is inference**: the `.jpa` assets are not in the
  repo, so the blend mode has not been read.

**"The sun seems tied to Link" — investigated 2026-07-26, no tie found**, and
**narrowed 2026-08-04**: ruling out vanilla's Link-following light rules out the
*runtime* light only. Vertex colours here do carry baked lighting (issue 10), so
it does not generalise into "nothing in the stream carries light".

**Two unknowns raised against the local light mirror outlived it**, having carried
over to effect lights: the churn cost in a busy room is unmeasured, and
`mFluctuation` is ignored, because honouring it means re-creating every flickering
light every frame. "The game flickers its torches and we do not" is a real
difference nobody has decided is wrong.

## Kakariko Village (F_SP109) crashes on entry — OPEN, 2026-08-16

**Reproduction (100%, no save dependency):** load any save in Hyrule Field, warp
to Kakariko Village. Crashes ~1.5 s after the camera cut. Loading a save that is
*already* in Kakariko crashes the same way; a new game (Ordon, F_SP102/108) is
fine.

The owner reports this has been broken "for the longest time" on D3D9/Remix
builds. **It was never written down anywhere in the three repos** — this entry is
the first record, which is most of why it was never worked.

### Signature
